# Drink Tracker — Backend: Database Foundation & Financial Logic

This delivers **only** the database foundation and financial calculation
logic, as scoped. No frontend, Kubernetes, AI, payment gateway, auth, or
REST endpoints are included.

## 3. Table relationships

- `users` 1—N `drink_sessions` (via `created_by`) — a user can create many sessions; a session has exactly one creator. Deleting a user who created sessions is **restricted** (`ON DELETE RESTRICT`) so historical sessions can't be orphaned by accident.
- `drink_sessions` 1—N `session_participants` — deleting a session cascades and removes its participant rows (`ON DELETE CASCADE`).
- `users` 1—N `session_participants` — deleting a user removes their participation rows (`ON DELETE CASCADE`).
- `users` 1—N `payments` (via `user_id`) — cascades on user delete.
- `users` 0—N `payments` (via `confirmed_by`) — nullable; if the confirming admin is deleted, `confirmed_by` is set to NULL rather than deleting the payment record (`ON DELETE SET NULL`).
- `(session_id, user_id)` is unique on `session_participants` — a user cannot be added twice to the same session.

## 4. Rounding algorithm

Implemented in `app/services/financial.py::split_amount()`. It **never**
uses `float`; everything is `Decimal`, converted to integer cents for the
actual division so there is no possibility of binary floating-point
drift.

Steps:
1. Round the total to exactly 2 decimal places (`ROUND_HALF_UP`).
2. Convert to integer cents (e.g. RM37.50 → 3750 cents).
3. `base_cents, remainder = divmod(total_cents, num_participants)`.
4. Every participant gets `base_cents`; the first `remainder` participants (in a stable, sorted-by-`user_id` order) get one extra cent each.
5. Convert back to Decimal money values.

This guarantees, by construction, that `sum(amounts) == total` exactly —
verified by an `assert` inside the function itself and by every test in
`tests/test_rounding.py`.

Example — RM37.50 split 4 ways: `3750 // 4 = 937 remainder 2` → two
participants get RM9.38, two get RM9.37 → sum = RM37.50 exactly, matching
the spec's example.

`split_session_cost()` wraps this for a list of participant user IDs: it
rejects duplicate IDs (DB also enforces this via the unique constraint)
and sorts IDs before splitting so the "who gets the extra cent" outcome is
deterministic and reproducible regardless of the order participants were
supplied in.

## 5. Configuring `DATABASE_URL`

Copy the example file and edit it:

```bash
cp .env.example .env
```

```
DATABASE_URL=postgresql+psycopg://username:password@host:5432/drink_tracker
```

`.env` is **not** included in this deliverable and should never be
committed — only `.env.example` (with placeholder values) is provided.
`app/core/config.py` loads `DATABASE_URL` via `pydantic-settings`
(`.env` support built in), and `alembic/env.py` also picks up
`DATABASE_URL` directly from the environment so migrations always target
the same database as the app.

## 6. Running Alembic migrations

```bash
cd backend
python3.13 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

export DATABASE_URL=postgresql+psycopg://username:password@host:5432/drink_tracker
alembic upgrade head
```

This was tested end-to-end against a real Postgres 16 database in this
session: `alembic upgrade head` created all 4 tables with correct types,
enums, FKs, indexes, and the `session_participants` unique constraint, and
`alembic downgrade base` cleanly reverses it. The app itself never
creates/alters schema at startup — Alembic is the only path to schema
changes.

To create a new migration after future model changes:
```bash
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

## 7. Running the tests

Tests need a real Postgres database (financial rounding tests are pure
Python and don't touch the DB, but the balance/constraint tests do). Use a
**separate** database from your dev DB, since the test fixtures create and
drop all tables:

```bash
export DATABASE_URL=postgresql+psycopg://username:password@host:5432/drink_tracker_test
cd backend
source .venv/bin/activate
pytest -q
```

Each test runs inside a transaction that's rolled back afterward, so
tests can be re-run repeatedly without accumulating data. All 34 tests
pass, including:

- Every rounding case from the spec (RM25/1,2,3,7,8 people; RM12.50/3;
  RM37.50/4,7) — each asserting `sum(amounts) == total` exactly.
- Multiple sessions accumulating into one balance.
- Pending, confirmed, and rejected payments (only CONFIRMED reduces
  balance).
- Partial payment → confirmation → remaining balance (RM20 owed, RM5
  confirmed → RM15 remaining, matching the spec example).
- DB-level enforcement of the "no duplicate participant in a session"
  unique constraint, and cascade-delete behavior.
